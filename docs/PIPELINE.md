# Решение: матчинг товаров

Справочник по решению. Отвечает на вопросы «что делаем», «почему именно так»,
«что уже пробовали» и «как это запустить».

---

## 1. Задача

Дано: каталог товаров (`id`, `name`, `attributes`, `category`) и список пар
`(id1, id2)`. Нужно для каждой пары предсказать, один ли это товар.

- **Метрика**: Macro Averaged PR-AUC — `average_precision_score` считается внутри
  каждой из 20 категорий и усредняется. Мелкая категория весит столько же, сколько крупная.
- **Формат выхода**: csv с колонками `id1,id2,predict`, строка на **каждую** входную пару.
- **Запуск**: Docker без доступа в интернет, на закрытых данных с **другими** товарами.
- **Объём теста**: сопоставим с `matches.parquet` + `items_human.parquet` (~365k пар, ~711k товаров),
  из них ~30% public, ~70% private.

---

## 2. Архитектура

**Одна модель, один проход. Ни бустинга, ни ансамблей, ни ручных признаков.**

```
пара (id1, id2) + каталог
        │
        ▼
preprocess_item()                    ← src/preprocess.py
   чистка + нормализация + сборка текста
        │
        ▼
tokenizer(текст1, текст2)            ← [CLS] A [SEP] B, max_length=384
        │
        ▼
BAAI/bge-reranker-v2-m3 (568M), голова на 1 логит
        │
        ▼
sigmoid → p(это один товар)
```

### Почему cross-encoder, а не эмбеддинги

Негативы в данных — **hard negatives**: пары уже предотобраны так, что товары похожи
(та же категория, близкие названия). Bi-encoder кодирует товары независимо и не видит
мелких различий — дозировки, размера, номера детали.

Проверено прямым замером: косинус `deepvk/USER-bge-m3` дал **0.3742**, дообученный
cross-encoder — **0.7750**. Разница в 2 раза. В категории «Аптека», где товары различаются
числом таблеток, разрыв девятикратный: 0.0905 против 0.8254.

Эмбеддинги остаются полезны для кандидатогенерации на полном каталоге 13.4M,
где cross-encoder по всем парам гонять нереально. В нашей задаче пары уже даны.

## 3. Предобработка — то, что заменяет фичи

Вся «инженерия признаков» ушла в сборку текста. Результат выглядит так:

```
автотовары | victor reinz прокладка впускного коллектора арт. 703315700 |
бренд: victor reinz | артикул: 703315700 | тип: прокладка двигателя | вид техники: легковые автомобили
```

Формат: `категория | название | ключ: значение | ключ: значение | ...`

### Что делает `preprocess_item`

| Шаг                                                                                            | Обоснование из данных                                                                                                    |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| html-теги,`&amp;`-entities, nbsp, zero-width, ` `, управляющие символы | 102k названий с двойными пробелами, 6.5k с entities, 2.8k с nbsp                                                |
| Схлопывание пробелов, нижний регистр                              | данные почти всегда уже lowercase, но на новых это не гарантировано                          |
| Склейка ключей-синонимов                                                    | `страна-изготовитель` (45%) + `страна производства` (22%) → `страна` (64%)                 |
| Выброс шумных ключей                                                            | `#хештеги`, габариты упаковки, гарантия, валюта — не различают товары              |
| Выброс значений-заглушек                                                    | `не указано`, `n/a`, `—` — шум; `да`/`нет`/`0` оставлены как настоящие значения |
| Обрезка значения до 100 символов                                         | в данных встретилось значение на**114 511** символов                                              |
| Обрезка названия до 300 символов                                         | максимум 4 200 — спам-перечисление партномеров                                                          |
| **Приоритетный порядок атрибутов**, максимум 16         | при обрезке в 384 токена решающее не должно потеряться                                           |

Приоритет: `бренд, модель, артикул, тип, цвет, размер, материал, состав, объём, вес товара г, вид техники, пол`. Остальные — по алфавиту, для детерминизма.

### Пер-категорийный приоритет атрибутов (готово, ждёт A/B)

Глобальный список приоритетов один на все категории, а решают в разных категориях
разные поля. Замер на 365k человеческих пар: для каждой (категория, ключ) считали,
во сколько раз совпадение значения поднимает вероятность матча.

Оказалось, что самые различающие ключи систематически выпадают из текста. Два механизма:

**Лимит 16 атрибутов.** Приоритетные ключи добавляются первыми и не режутся,
а всё остальное идёт по алфавиту и обрывается. Доля товаров с >16 атрибутов:
Мебель 64.7%, Бытовая техника 45.2%, Ювелирные изделия 44.7%, Аптека 38.9%,
Электроника 36.3%, Обувь 34.3%, Одежда 31.1%.

| Категория                         | Ключ                | Различает | Терялся |
| ------------------------------------------ | ----------------------- | ------------------ | -------------- |
| Электроника                     | чипсет            | ×17978            | 97.5%          |
| Мебель                               | ширина, см      | ×3.97             | 89.0%          |
| Электроника                     | тип памяти     | ×3.21             | 80.4%          |
| Строительство и ремонт | тип цоколя     | ×1.54             | 52.2%          |
| Аптека                               | форма оправы | ×3.79             | 51.7%          |
| Ювелирные изделия          | страна            | ×3.75             | 37.7%          |
| Обувь                                 | страна            | ×2.64             | 34.8%          |
| Одежда                               | страна            | ×6.38             | 26.6%          |

**Обрезка по 384 токенам** режет конец строки. Доля пар за лимитом:
Аптека 56.5% (медиана пары 399 токенов!), Электроника 25.8%, Товары для животных
20.1%, Бытовая техника 18.9%, Продукты 17.9%, Ювелирка 17.4%, Мебель 15.9%.
А вот в Обуви 0.1% и Одежде 0.9% — **в fashion обрезка по токенам не при чём,
там бьёт только лимит 16**.

Это объясняет, почему LoRA-специалист по Аптеке дал самый слабый прирост
(+0.0055): решающие «оптическая сила» (×14.2) и «форма оправы» (×3.8) сидели
в хвосте, и модель их не видела.

**Что сделано.** `build_item_text(..., per_category=True)` строит порядок как
`CORE_KEYS` (бренд, модель, артикул, тип) → список для этой категории → общий
список → алфавит. Лимит поднят с 16 до 24 в шести категориях с короткими
текстами (p95 ≤ 350 токенов). Списки в `CATEGORY_PRIORITY_KEYS`, построены
по данным: вес = покрытие × log(отношения).

Замер эффекта на 30k товаров: текст меняется у 60.1% товаров, все ключи из
таблицы выше теряются теперь в 0% случаев, доля обрезанных пар растёт
незначительно (10.0% → 10.7%), медиана длины +4 символа.

⚠️ Флаг по умолчанию **выключен**: v4 и все адаптеры обучены на старом порядке,
включение без переобучения даст рассинхрон train/serve. Регрессия проверена —
при `per_category=False` тексты совпадают со старыми на 30 000 товарах точно.

### Почему нет отдельных признаков brand_match / artikul_match

Они не нужны: бренд и артикул стоят **в начале обеих строк**, и cross-attention
сравнивает их напрямую. Проверено — см. раздел 6.

### Единый источник правды

`preprocess.py` используется и при обучении, и в инференсе. Функция чистая и
детерминированная, без обучаемого состояния — поэтому текст, на котором строилась
модель, гарантированно совпадает с тем, что подаётся в рантайме.

Для инференса модуль тянет только stdlib (`html`, `json`, `re`) — `polars` импортируется
лениво внутри батч-функции. Это защита от того, что в Docker-образе может не оказаться polars.

## 4. Обучение

### Итоговый рецепт

```
1. Предобучение на LLM-парах       600k пар, lr 2e-5, 1 эпоха
2. Продолжение на LLM-парах        +1.5M свежих пар, lr 1e-5
3. Replay-дообучение               human 292k + LLM 292k (1:1), lr 1e-5
```

Общие параметры: batch 64, max_length 384, bf16 autocast, AdamW (weight decay 0.01),
linear schedule с 5% warmup, grad clip 1.0, `BCEWithLogitsLoss`.

### Два приёма, которые важны

**Случайная перестановка сторон пары.** Матчинг симметричен, а `[SEP]` — нет.
Без этого модель учит асимметричную функцию.

**Группировка батчей по длине.** Медиана пары 251 токен, p95 — 392. Случайный батч
паддится до ~450, сгруппированный — до своей длины. Ускорение ×1.5 без потери контекста.

⚠️ Здесь был баг: сортировка применялась и при `shuffle=False`, из-за чего на валидации
скоры разъезжались с метками и метрика падала до случайной. Обнаружен по тому, что
результат в точности совпал с константным предсказанием (0.2611). Исправлено —
порядок обхода запоминается и скоры раскладываются обратно.

### Почему LLM-данные, а не больше эпох на человеческих

Вторая эпоха на человеческих парах **переобучает**: loss падает 0.2963 → 0.2208,
а валидация проседает 0.7750 → 0.7509. 292k пар на 568M параметров хватает на одну эпоху.

### Почему replay, а не последовательные стадии

Чистое дообучение на человеческих парах после LLM-предобучения роняло генерализацию
0.7309 → 0.6683 — модель забывала разнообразие товаров. Подмешивание LLM-пар 1:1
сохранило её, и обе метрики начали расти одновременно.

## 5. Как меряем

Две валидации, потому что ни одна по отдельности не описывает тест.

| Набор      | Что это                                                                                                                              | Что меряет                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| `human_val`   | 73 313 пар, человеческие метки, сплит по компонентам связности графа пар            | конвенцию разметки                     |
| `llm_holdout` | 60 000 пар из`matches_llm` с уверенными метками, товары не пересекаются с обучением | генерализацию на новые товары |

### Почему human_val обманывает

`human_val` даёт 0.7750, лидерборд — 0.4454. Разрыв 0.33.

Проверены и отброшены:

- **Баг в сабмите** — константное предсказание дало бы 0.2611, а не 0.4454.
- **Утечка в валидации** — на «чистых» парах без дословных двойников в train метрика
  оказалась даже **выше** (0.7981 против 0.7118 на «протёкших»).

Осталась верная причина: **охват каталога**. Человеческая разметка покрывает 711k
товаров, тест берёт другие из 13.4 млн. Валидационные товары не участвовали в обучении,
но они из того же узкого среза.

### Калибровка прокси по лидерборду

| Сабмит | llm_holdout | Лидерборд |
| ------------ | ----------- | ------------------ |
| v1           | 0.5927      | 0.4454             |
| v3           | 0.7269      | 0.5074             |
| v4           | 0.7440      | 0.5214             |

Перенос **нелинеен**:

| Участок | Прирост прокси | Прирост LB | Коэффициент |
| -------------- | --------------------------- | ----------------- | ---------------------- |
| v1 → v3       | +0.1342                     | +0.0620           | 0.46                   |
| v3 → v4       | +0.0171                     | +0.0140           | **0.82**         |

Возле текущей точки доходит 82% прироста, а не 46%. Ранняя оценка по двум точкам
(«для LB 0.60 нужен прокси 0.93, это нереально») была **ошибочной**: экстраполяция
линейная, а зависимость таковой не является. Вероятное объяснение — на первом участке
менялись одновременно данные и рецепт обучения, поэтому часть прироста на прокси была
непереносимой; на втором рецепт зафиксирован, менялись только данные.

Пересчёт целей по локальному коэффициенту 0.82: LB 0.55 требует прокси ~0.779,
LB 0.57 — ~0.803, LB 0.60 — ~0.840.

### Ожидаемое расхождение public/private

Бутстрап на нашем val в пропорции 30/70 (200 разбиений): медиана |public − private| = 0.0054,
p90 = 0.0132. С поправкой на размер теста — **ожидаемо ~0.002, максимум ~0.006**.
Разрыв заметно больше означал бы, что разбиение неслучайно.

## 7a. Категории: разбор и три отрицательных результата

Метрика — macro по 20 категориям, поэтому напрашивается работа с отстающими.
Проверено три захода, все отрицательные.

### Балансировка по количеству — нечего балансировать

Доли категорий в обучающей смеси: **4.15–6.02%** при идеале 5%. Веса вышли 0.83–1.21,
то есть поправка в пределах шума. Организаторы насэмплировали категории равномерно.

### «Слабые категории» — артефакт баланса классов

По абсолютному AP на `llm_holdout` fashion выглядит провально: Обувь 0.213,
Одежда 0.302. Но у average precision нижняя граница равна доле положительных,
а она там **2.7%** против 9.9–11.8% в человеческих данных.

С поправкой на базу картина обратная:

| Категория                   | AP    | База | Lift             |
| ------------------------------------ | ----- | -------- | ---------------- |
| Одежда                         | 0.302 | 0.027    | **11.1×** |
| Ювелирные изделия    | 0.467 | 0.041    | **11.4×** |
| Обувь                           | 0.213 | 0.027    | 8.0×            |
| Бытовая химия            | 0.904 | 0.344    | **2.6×**  |
| Товары для животных | 0.902 | 0.271    | 3.3×            |

Категории с худшим AP — лучшие по относительному качеству, и наоборот.
Вкладываться в них смысла нет: модель там уже работает лучше всего.

**Методический вывод:** AP нельзя сравнивать между наборами и категориями с разным
балансом классов. Сравнивать надо lift над базой.

### Размеры — сигнал слабый

Внутри Одежды (база 0.118) дословное совпадение размера даёт P(матч) 0.151, то есть
lift всего **1.28×**; в Обуви 1.30×. Для сравнения, совпадение артикула — 3.47×.
Нормализация записи (`40 40 ru` → `40`, запятая → точка, диапазоны) затрагивает
**320 пар из 365 654**. Подсказывать модели признак, который сам почти не несёт
сигнала, бессмысленно.

## 7b. Специалисты по категориям — прирост на прокси

⚠️ Ветка закрыта: лидерборд прироста не подтвердил, см. §7c.

Ниже — как это выглядело по прокси-метрике, прежде чем лидерборд вынес вердикт.

### Наблюдение

Дообучение v4 **только на парах одной категории** (её человеческие пары + её LLM-пары,
lr 5e-6, ~1500 шагов) улучшает качество в этой категории:

| Категория                | AP базовый | llm_holdout после | Δ                |
| --------------------------------- | ----------------- | ---------------------- | ----------------- |
| Обувь                        | 0.2135            | 0.2640                 | **+0.0505** |
| Одежда                      | 0.3016            | 0.3576                 | **+0.0560** |
| Ювелирные изделия | 0.4680            | 0.5070                 | **+0.0390** |
| Мебель                      | 0.8627            | 0.8812                 | +0.0185           |

`human_val` при этом не страдает (−0.004…+0.013). Чем ниже исходный AP, тем больше выигрыш.

### Контроль: это не «просто больше обучения»

Те же 1500 шагов на **полной** смеси вместо одной категории:

| Категория                | v4     | Контроль | Специалист |
| --------------------------------- | ------ | ---------------- | -------------------- |

## 7c. Специалисты по категориям: лидерборд сказал «нет»

Сабмит `v4 + 12 LoRA-адаптеров` дал на лидерборде **0.52157** против **0.5214** у чистого
v4. Прирост **+0.0002** — ноль при ожидавшихся +0.010.

### Что это означает

Адаптеры отбирались по правилу «взять, если вырос `llm_holdout` в своей категории».
Все 12 прошли отбор, суммарно +0.1682 → **+0.0084 к macro на прокси**. При этом
`human_val` у них в среднем **падал** на 0.0065. Лидерборд оказался ближе к `human_val`.

Объяснение: `llm_holdout` меряет две разные вещи сразу — охват каталога и конвенцию
LLM-разметки. Прирост v1 → v3 → v4 шёл от охвата и переносился на лидерборд
с коэффициентом 0.46–0.82. Прирост от специализации идёт от подгонки под конвенцию
LLM внутри категории: адаптер учится на LLM-парах своей категории и меряется
на LLM-holdout той же категории. На человеческой разметке теста это не работает.

**Методический вывод:** `llm_holdout` нельзя использовать как единственный критерий
отбора. Он валиден для изменений, добавляющих охват каталога, и врёт для изменений,
подгоняющих модель под конвенцию разметки. Отбирать надо по обеим осям сразу.

Ветка закрыта: раскатка остановлена на 12 категориях из 20, оставшиеся 8 не считались.
Инфраструктура (слияние LoRA без `peft`, группировка пар по категории) сохранена
в `solution/src/inference.py` — она рабочая и сверена, просто применять её не к чему.

## 7f. Лидерборд по v6: рост `human_val` оказался признаком переобучения

`solution_v6` (пер-категорийный препроцессинг + два дополнительных прохода replay)
дал на лидерборде **0.51745** против **0.5214** у v4 — **минус 0.004**, при том что
обе локальные метрики были лучше.

| Сабмит          | Эпох по human    | `human_val` | `llm_holdout` | Лидерборд |
| --------------------- | ---------------------- | ------------- | --------------- | ------------------ |
| v1                    | 1 (только human) | 0.7750        | 0.5927          | 0.4454             |
| v3                    | 1                      | 0.7686        | 0.7269          | 0.5074             |
| **v4**          | **1**            | 0.7761        | 0.7440          | **0.5214**   |
| v4 + адаптеры | 1                      | ~0.772        | ~0.752          | 0.52157            |
| v6                    | **3**            | 0.7887        | 0.7485          | 0.51745            |

### Разбор

v6 отличался от v4 **двумя** вещами сразу: новым порядком атрибутов и двумя
дополнительными проходами replay. В каждом проходе смесь включает все 292k
человеческих пар, поэтому модель увидела их трижды против одного раза у v4.
LLM-пары каждый раз брались свежие, человеческие — повторялись.

Рост `human_val` 0.7761 → 0.7887 объясняется не улучшением модели, а заучиванием
человеческой разметки: валидация отделена по компонентам связности, но берётся
из того же узкого среза каталога, что и обучение. На тесте товары другие,
и заученное не переносится.

**Это воспроизводит более ранний результат** «вторая эпоха на human переобучает»,
который был получен на чистом дообучении и ошибочно сочтён неприменимым к replay.

### Что из этого следует для методики

Ни одна из двух локальных метрик не является достаточным критерием:

- `llm_holdout` растёт от подгонки под конвенцию LLM (см. §7c, адаптеры);
- `human_val` растёт от заучивания человеческой разметки (этот раздел).

Обе оси можно поднять, ухудшив решение. Единственная защита — **фиксировать
число эпох по человеческим парам** (одна, как в v4) и менять что-то одно за раз.
Изменения, требующие дообучения, надо сравнивать с v4 **от той же точки**
(`/tmp/matching/ce_scale/best_llm1b`) и при том же числе проходов.

этот прогон обошёл её ещё на середине пути (34%) и продолжил расти дальше.
Это лучший результат за всю сессию с большим отрывом.

`human_val` держался около 0.68 всю стадию — ожидаемо: cover не видит
человеческих пар вообще, конвенция разметки временно забыта.

Там прирост шёл от специализации по категориям — модель подгонялась под
конвенцию LLM-разметки внутри узкого среза, и на лидерборде это дало почти ноль

это должно дать заметный прирост, а не шум.

Собрано в `solution_cover.zip`. Это первый кандидат сессии, который меняет

## 8a. Отладочная сборка (`solution_debug.zip`)

На случай падения в закрытом окружении организаторов: у нас нет доступа ни к их
файловой системе, ни к их логам сверх того, что попадёт в stdout контейнера.
`solution_debug.zip` — та же модель (`ce_cover/best_human`), что и в
`solution_cover.zip`, но `run.py` инструментирован:

- **трассировка шагов** (`step()`): каждый пройденный этап логируется с временной
  меткой — от разбора аргументов до записи csv;
- **дамп при падении**: любое исключение перехватывается, печатается в stdout
  и по возможности пишется в `debug.log` рядом с выходным файлом. В дампе —
  traceback, пройденные шаги, аргументы запуска, наличие/размер/схема
  `items_path` и `matches_path`, по 5 примеров строк из каждого (строки обрезаны
  до 200 символов), версии библиотек (torch/transformers/pyarrow/peft/safetensors),
  доступность и модель GPU, содержимое каталога с весами;
- **код возврата не маскируется** — после дампа исключение пробрасывается дальше,
  процесс всё равно завершается с ненулевым кодом.

### Проверено

- Успешный путь: предсказания **бит-в-бит идентичны** обычной версии (diff чистый).
- Путь с падением (несуществующий `matches_path`): дамп собрался, код возврата 1.
- Каскадное падение (битый `items_path`, не parquet): `_file_info` перехватывает
  ошибку чтения схемы отдельно, сама диагностика не падает.
- Размер дампа — единицы килобайт («небольшой лог», как просили), не десятки МБ.

⚠️ Не для отправки как основной сабмит — это диагностический вариант того же
кандидата, держать под рукой на случай, если реальный сабмит упадёт без единой
подсказки почему.

### ⚠️ Отказ в образе организаторов: `polars`

Сабмит упал на старте с `ModuleNotFoundError: No module named 'polars'` —
в `src/preprocess.py` импорт стоял на уровне модуля.

```
File "/workspace.../src/preprocess.py", line 23, in <module>
    import polars as pl
ModuleNotFoundError: No module named 'polars'
```

`polars` и `pyarrow.parquet` нужны только офлайн-функции `preprocess_frame`,
которая в рантайме не вызывается. Исходная копия в `solution/src/` была написана
с ленивым импортом именно от этого риска; при синхронизации копий она была
перезаписана офлайн-версией из `scripts/`, и защита исчезла.

**Правило: `scripts/preprocess.py` и `solution/src/preprocess.py` нельзя
синхронизировать слепым копированием.** У них общая логика, но разные требования
к зависимостям: офлайн-версии нужен `polars`, рантайму — нет. Импорты тяжёлых
библиотек в версии для сабмита обязаны быть внутри функций.

**Как проверять перед отправкой** — воспроизвести отсутствие модуля:

```python
import sys
class Blocker:
    def find_module(self, name, path=None):
        return self if name.split('.')[0] in ('polars', 'pyarrow') else None
    def load_module(self, name):
        raise ImportError(name)
sys.meta_path.insert(0, Blocker())
import preprocess          # должно импортироваться без ошибки
```

Что известно про образ по факту падения: `pyarrow` в нём **есть** (импорты
`pyarrow.compute/dataset/parquet` в `run.py` отработали до падения),
`polars` — **нет**. Про `peft` неизвестно, поэтому слияние LoRA в
`src/inference.py` сделано на голом torch.

### Что заложено под требования проверки

- **Работа без интернета**: `HF_HUB_OFFLINE=1`, `local_files_only=True`, веса в архиве.
- **Результат для каждой пары**: если товара нет в каталоге, пара всё равно попадает
  в выдачу со скором `FALLBACK_SCORE = 0.0`. Есть `assert` на сохранность числа строк.
- **Экономия времени**: из каталога подгружаются только товары, встречающиеся в парах.
- **fp16**: архив вдвое меньше (1.1 ГБ против 2.2), предсказания бит-в-бит те же —
  инференс и так шёл в fp16.
- **Сортировка по длине** на инференсе: паддинга почти нет.

### Проверено

- Метрика упакованного решения на val воспроизводит метрику обучения с точностью 0.0003
- Запуск из распакованного архива в чистой папке даёт тот же выход
- Формат csv, число строк, целостность архива

⚠️ **Не проверено**: запуск внутри реального образа `odsai/ecup26-matching-baseline:1.0` —
в среде разработки нет Docker.

⚠️ **Не сделано — блокирует сабмит со специалистами.** Текущий `src/inference.py`
грузит одну модель через `AutoModelForSequenceClassification` и не знает про LoRA:
ни `peft`, ни переключения адаптеров в коде нет. Чтобы адаптеры из `rollout.py`
попали в сабмит, нужно:

1. группировать пары по категории товара (категория берётся из каталога);
2. под каждую группу подключать свой адаптер, для категорий без адаптера
   работать базовой моделью;
3. проверить, что `peft` есть в образе организаторов — иначе слить веса
   адаптера в базовые (`merge_and_unload`) заранее и возить 20 полных моделей
   нельзя по размеру, значит сливать придётся на лету при загрузке;
4. пересчитать время инференса: переключение адаптера на каждую из 20 групп
   добавляет перезагрузку весов, а сортировка по длине теперь внутри группы.

⚠️ **Место на диске JupyterHub.** `/home/jovyan` — это tmpfs на 20 ГБ, свободно
5.4 ГБ. Архив с базой и 20 адаптерами (~3.4 ГБ) там не соберётся рядом с уже
лежащим `solution_v4.zip` (1.15 ГБ). Собирать надо в `/tmp` — это overlay
на 200 ГБ, свободно 108 ГБ. Там же лежат все чекпоинты (`/tmp/matching`, 24 ГБ).
**`/tmp` не переживёт перезапуск пода** — перед пересборкой убедиться,
что нужные адаптеры скопированы.

```bash
docker run --rm --gpus all -v $PWD:/w -w /w odsai/ecup26-matching-baseline:1.0 \
  python -u run.py -i items.parquet --matches_path matches.parquet -o submit.csv
```

### Производительность

~440 пар/сек на L40S без конкуренции → **~15 минут** на 365k тестовых пар.
Модель занимает 1.1 ГБ весов, около 3 ГБ VRAM при инференсе.
